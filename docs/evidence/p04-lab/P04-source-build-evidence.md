# P04　T1限定登録とcollector中止通知の実装・検証結果

検証対象は、依頼で指定されたVM-AのT1を想定したソースとビルドです。WindowsとLinuxで同じGitツリーを使って合成試験を行い、Windows AMD64では登録境界、collector、launcherの3本をDebugとReleaseで実際にリンクしました。実デバイスに登録した実績やVM-Aでの停止・復元実績は、今回の成績に含めていません。

## 実装した動作

**登録対象の選択。** 保護するOSディスクとT1を別々の記録から照合します。デバイスの同一性、親の位置、LUN、ホスト側のディスク連鎖、特殊用途、既存のスタックが一貫し、T1が1台だけに決まった後で、既知の8 GiB・RAW・パーティション0件を確認します。番号の変更を許容し、同型同容量のOSディスク、重複ID、用途不明、取得不能を拒否します。個体判定は保守的に扱い、登録候補では199文字以内の対応ASCII表現を要求します。selector形式自体は終端を含む512 UTF-16コード単位です。[MicrosoftのデバイスインスタンスID仕様](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/device-instance-ids)

**登録の途中失敗。** パッケージ配置、要求時起動サービスの準備、selectorの確定、T1の既存UpperFilters末尾への1件追加を順番に扱います。合成環境では試みた変更、実際に残った変更、独立した読み戻しを比較します。APIがエラーを返しても変更が残る場合、プロセス消失、記録欠損、世代・排他の変化は確認済みの範囲で打ち切ります。自動再送や既存リストの一括書き戻しはありません。Windowsの実APIを呼べる部分は非公開のリンク検証対象です。

**collectorの停止。** 制御付き収集では試行専用の無名イベントを使い、子には待機権限だけを渡します。BEGIN前の中止はarchiveを作らず終了値5。有効なBEGIN後は同じ所有者が通常のDRAINを打ち切り、新しいcall IDでSTOPと許された回収を行います。応答不明のDRAINは再送しません。従来のCLIとnative archive v1を維持し、有効なarchiveを出力した場合の終了値は4です。

**同期I/Oと証跡。** 起動から15,000 msの時点で同期呼び出しが戻らない場合は「停止未確認」と記録します。遅れて確認した終了は別の時刻に記録します。要求の発行、所有者の受理、STOP応答、終端、子の終了、受信バイト数・SHA-256、転送完了、外部保存は別項目です。stdoutの失敗時も、既に起動した診断の受信処理を待ってから結果を返します。ゲストの外での監視とR1復元は運用上の別工程です。

## 固定したソースの実測

件数には同じケースの別OS・別プロファイルでの実行が含まれます。18件はRelease試験の中で収集した証跡です。合格した試験名、入力の種類、期待列に照合した実際の呼出列、終了値、ソース・ログのSHA-256は `evidence/windows/` と `evidence/linux/` にあります。登録ではP/S/K/F各段階の失敗を扱い、独立したfake子プロセスの強制終了・再起動を含みます。不帰還試験は該当呼び出しを別プロセスの中で実際に保留し、外部の監視担当が期限を記録した後で試験装置だけが解放しました。

**誤登録を検出する試験の確認。** 固定版のコピーで正しく同定したT1を保護OSのオブジェクトに差し替えると、R02が狙ったアサーションで失敗し終了値101を返しました。元のソースのハッシュは一致しました。容量、ID、空のクラス基準を通す3種類の誤変更も個別の試験で検出しました。読み戻しについては、APIの戻り値またはfake内部の正解だけで効果を判定する2種類の誤変更を別のコピーで検出しています。対応するファイルは `wrong-target-mutation.json`、`admission-mutations.json`、`readback-mutations.json` です。

**ビルド。** Rust 1.99.1、Windows SDKパッケージ10.0.26100.6584、Microsoft Cコンパイラ19.44.35230、リンカー14.44.35230を使用しました。3本を `x86_64-pc-windows-msvc` でcheckした後、DebugとReleaseのPE実体について、別々にimportテーブルと `dumpbin` の表示を照合しました。登録用PEはSetupAPI、SCM、レジストリなどの25個の必須インポートを保持します。SDKヘッダーを用いたCのABI検査もコンパイルしました。各PEのSHA-256とインポートは `evidence/windows/linked-images.json` にあります。Windowsの実行を伴うIPC試験には合成専用workerを使いました。

**既存ゲートと実行環境。** 両OSでformat、Clippy（警告をエラー扱い）、workspaceテスト、計画文書検査が通りました。Windowsでは既存のGit Bash試験がサンドボックス内で `0xC0000022` になったため、既存xtaskの25件を通常のWindowsユーザーで別に実行し、表の合計に含めました。LinuxはローカルWSLのDebianで、非rootのまま実行しました。SDKとツールは作業ディレクトリ内に用意しました。SDKパッケージのハッシュと個々のMicrosoftコンパイラの署名を確認しています。Visual Studioチャネル全体のカタログの真正性までは確定していません。

ABI検査で実際に読み込まれた104種類のヘッダーと、Debug／Releaseのリンク記録に明示された8つのSDKライブラリは、各配布パッケージ内のファイルとバイト単位で一致しました。コンパイラ・リンカーの版とハッシュ、元のABIオブジェクト、include追跡用に再コンパイルしたオブジェクトは `evidence/windows/toolchain-inputs.json` で個別に確認できます。R02の初回は元ログのハッシュだけを記録したため、同じ合成バイナリで失敗を再現し、匿名化した再実行ログと両方のハッシュを同梱しました。

## 使用範囲と残る判定

実Windowsへの適用入口は閉じています。配備可能な署名済みINF・CAT・SYS一式、他のinstaller／PnP書き手との排他、パスの差し替えを防ぐ運用、実際の装着位置と制御デバイスの実効ACL、ゲスト障害時に独立して動くホスト監視・復旧は未検証です。カーネル境界に変更はなく、今回の対象について従来のWDKドライバーを再リンクした成績は計上していません。VM-A、T1、R0、R1に対する操作はなく、実機登録、署名、ロード、観測、GitHub投稿も実施していません。

アーカイブ内のエビデンスはテキストとJSONです。各コマンドの成否と元ログのハッシュを保存し、共有用ログには試験名・結果・合成証跡を抜粋しました。実行ファイルや私的な識別子は同梱していません。
