## 指摘と修正の確認

| 発見した問題 | 受け入れた修正と根拠 |
|---|---|
| 登録コードで、従来型のSetupAPIが使うUpperFiltersの番号と別のプロパティ番号を混同していた | SDKと照合し、従来型APIの読み取り・書き込みがともに17、統合プロパティキーのPIDは19であることを、実際に下位の関数へ渡した引数で別々に検査した |
| 発行時刻、試行の対応、受信データを追跡する情報が不足していた | 通知が成功した時刻、匿名試行ID、受信バイト数とSHA-256を個別に記録。送信者消失、STOP応答、プロセス終了、保存確認の意味も区別した |
| 親と子の診断を同じstderrへ並行して書くと、JSONの途中に別の記録が入り得た | 子の断片を完全なレコードに組み立て、同一試行の識別子を付けて一つの出力担当へ渡す。断片化、途中EOF、過大入力、書き込み失敗を試験した |
| バイナリ出力の失敗を先に返すと、並行受信中の最終診断を失う可能性があった | 出力、プロセス待機、終了コード照会の失敗について、開始済みの両方の受信処理が終了するまで結果を返さない。二つ目の受信処理を開始できない場合も、一つ目を待って診断未完了を記録する。4条件を同期点付きの回帰試験で確認した |
| 登録のWindows境界と証跡だけでは、配置・サービス準備や部分適用の判定を裏づけきれなかった | 配置、サービス準備、selector、T1のフィルター設定の各境界を確認。サービスの未承認ImagePathを開かないこと、エラー後の実効果を読み戻しで判定すること、実適用入口が閉じていることを照合した |
