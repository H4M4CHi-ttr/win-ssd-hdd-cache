# P04 別契約案　VM-AのT1登録・デバイス再始動・初回ロード

**状態は未承認・実行NO-GO。** 本案で所有者が将来承認できるのは、指定した署名済みパッケージを使い、VM-AのデータディスクT1にP04を登録し、T1のデバイス再始動とP04の初回ロードを伴う適用を**1試行だけ**行い、装着位置を確認すること。三つの動作の間に人が介入できるという前提を外す。今回の依頼は本文とゲスト用プロンプトの作成・レビューまでである。

2026年11月20日。D01はVM-AのOSディスクの匿名名。登録後も未ロードのまま最終確認を行う[旧仕様](P04-T1-cancel-spec.md)と、旧方式の[排他・配備のNO-GO判定](P04-T1-registration-exclusion-and-package-scope.md)はそのまま有効である。固定ソースのツリーは `f1fb5c4f9f459edd2aeebfc490bef246f4a2f7d7`。配布済みソースZIPにはprimitive形式のINFが1件あり、CAT・SYSは各0件。実適用の関数は常に拒否を返す。本案向けの登録経路と署名済み配布物は未受入である。[実装のレビュー記録](P04-source-build-review.md)／[宣言的登録の調査](P04-T1-declarative-filter-decision.md)／[本案とゲスト用プロンプトの独立レビュー](P04-T1-registration-restart-first-load-review.md)

## 1　所有者が一度に許可する範囲

| 項目 | 本案の取り決め |
|---|---|
| 適用の開始と終了 | 承認はDriver Storeへの配置など、最初に状態が変わり得る操作の**前**に得る。署名済み一式の配置から、T1への登録、WindowsによるT1の再始動、指定SYSの初回ロード、適用後の読み取り確認までを一つの承認に束ねる。変更を発行する適用は1回限り。自動再始動に手動の再始動を重ねない。読戻し完了、異常停止、期限超過のいずれかで適用権限を使い切る。 |
| ゲスト共通の効果 | 承認票に実名・ハッシュを私的に固定した**1パッケージ、1サービス、T1専用selector**の準備と、P04が所定の装着時に作る制御デバイスとシンボリックリンクの生成を明記する。通常のDriver Store・カタログ・サービスの管理更新はD01上のOS領域に発生する。この書込みも許容できない場合は開始できない。 |
| 保護する範囲 | デバイス構成を変更してよいのはT1だけ。D01、他のdevnode、親コントローラー、DiskDriveクラス、既存の機能ドライバー・フィルター、volume・dump構成への変更要求は0件とする。ゲストOSやホストの再起動、VM設定変更、二度目の適用・再始動・再ロードは対象外。 |
| 観測との境界 | この試行は装着の確認で終える。collector起動、CDO（P04の制御デバイス）を開く試験・IOCTL、`BEGIN`、意図的なストレージI/Oは含めない。T1は未初期化・未フォーマットのまま。Secure Boot・HVCI・テスト署名などの変更、署名作業、Verifier、抜去・強制電源断にも許可を与えない。制御デバイスの既定の権限と上書き設定は事前に審査し、予定外の公開や権限差があれば停止する。 |
| 試行の終了と復旧 | 所有者は同じ承認票の**別欄**で、指定条件下のゲスト正常終了、ホストからR1への復元、復元確認のための通常起動をあらかじめ許可できる。初回の単発試行は成功時もR1へ戻す。以前のVM準備時の許可は今回の試行に流用しない。承認済みの範囲なら、各動作の間で再承認を求めない。 |

## 2　最初の副作用を許せる条件

ゲスト担当は[読み取り専用プロンプト](P04-guest-readonly-targeting-and-stack-prompt.md)の事前照会（PRE）を使う。所有者と審査担当は、次のすべてについて根拠と有効範囲を承認票に記す。

1. **個体と保護用途。** ホスト担当がVM-A、R0の子である停止時R1、OSとT1の現在の差分から元VMDKまでの連鎖を私的に照合する。ゲスト担当はOS・EFI/boot・pagefile・dump等の所在からD01を保護し、ストレージ固有ID、シリアル、完全なPnPインスタンスID、親の位置とLUNを一つの記録に対応づける。D01とT1が別々に各1台、T1は8 GiB・RAW・区画0で特殊用途なし。番号、容量、名前だけでは確定しない。AFTER_R1のbuild `26300.9974` と構成は比較用の過去値で、今の状態は再照合する。
2. **Windowsが照合する対象。** 候補は署名済み拡張INFによるデバイス固有の `DDInstall.Filters / AddFilter`。有効な全Models行・適用セクション・参照先を当該build/archで評価する。T1に一致し、D01に一致せず、他の適用可能な対象への一致と未評価が各0件であること。肯定条件だけなら、INFが採用したIDのうち一つでもD01に一致すれば不合格。除外に依存する案は `ExcludeID` の位置と実効結果まで審査する。完全なinstance IDでの個体同定、署名、ExtensionId、VM共通のCHIDはこの判定を代替しない。[Modelsの照合][models]／[拡張INFの選択][extension]／[ExcludeID][exclude]
3. **パッケージを置いている全期間。** 現在接続中の2台が異なるだけでは足りない。対象になり得る他のdevnode、非接続・再列挙・再登場し得る機器と一致する可能性を、静的な適用範囲と固定したVM構成で評価する。最初の配置からR1復元確認まで、保護対象への遅延適用を許さない。区間・対象を限定できないときは開始しない。ハードウェア変更、別installerの介入、予定外のPnPで承認時の条件と一致しなくなれば停止する。R1による復旧は、誤適用の許可にはならない。[Driver Storeの自動適用][store]
4. **位置の見込みと確認方法。** D01とT1の既存構成、`partmgr` の登録元、両台に適用された基本INF・節・版、上位フィルターのレベルと並びを確認する。狙う位置はT1の `disk` 直上かつ `partmgr` の下である。レベル未定義、同一レベル内の任意順序、既存のクラス登録との関係不明により候補位置を説明できなければ開始しない。PREで将来の装着位置を実測済みにはしない。POSTで該当する二つのデバイスの実スタックを識別できる、既設・承認済みの読み取り証拠と担当を先に指定する。[フィルター順序][order]／[AddFilter][addfilter]
5. **配布物と最初のロード。** 最終INF・CAT・SYS・実行主体を固定する。カタログの信頼、INFと全参照ファイルの収録・実ハッシュ、現行の署名方針・HVCIとの整合、検査から使用までのファイルのすり替え防止を確認する。関連する全セクションと依存を展開し、付随パッケージ、対象外のインストール、機能ドライバー置換やクラス編集、共有サービスの上書きが生じる案は採用しない。P04は開始前に未登録・未ロードで、T1以外に残存参照がないこと。専用サービスは要求時起動とし、手動でサービスを起動しない。準備に必要な変更も承認票に含める。[Driver Store][store]／[カタログの検証][signature]／[CopyINFの再帰処理][copyinf]
6. **selectorの先行を証明する。** P04は `DriverEntry` で `TargetInstanceId` を一度だけ読む。PREで未登録・selector未設定なのは正常である。事前審査では順序を保証する設計と失敗試験を確認し、承認後の試行内で実値を照合する。初回ロードが**起こり得る最初の時点より前**に、私的に照合したT1の完全なIDが正しい `REG_SZ` として確定・読戻し済みで、初回ロードまで保護されることを示す。先に用意するサービス・selectorがあるなら、その作成順・権限・所有と失敗時の効果を実物とサポートされる経路で審査する。配置でPnPが先に動き得るなら、配置後にselectorを設定する計画は不合格。新契約でまとめる三動作も、この先行条件は解除しない。[固定実装のレビュー](P04-source-build-review.md)／[PnPのロード条件][load]
7. **競合と失敗を封じ込める。** 新案ではP04による旧 `UpperFilters` リスト全体の置換を使わず、OSの宣言的登録を使う。登録・装着・再始動の許容先はT1だけとし、必要なパッケージ・サービス・selectorは他の書き手と取り違えたり上書きしたりできない仕組みを求める。第三者のすべての活動を停止する保証は置かない。外部変更を上書きし得る操作や、相手の操作と区別できない結果が残る場合は不合格とする。待機APIの成功、独自mutex、更新後に値が元と一致したことだけでは受け入れない。外部の全活動を排除する旧REG-3の保証が引き続き必須なら、本案に移行しない。[PnP待機API][wait]／[旧方式の排他評価](P04-T1-registration-exclusion-and-package-scope.md)
8. **監視と復元。** ホスト担当がゲスト外で応答と期限を監視でき、R1にOS・T1の両方が通常モードのディスクとして含まれることを確認する。両ディスクとスナップショット差分・作業先の当日の空き、ホスト認証・復元先も確認する。失われるR1以後の状態と私的証跡の退避を所有者が了承する。正常終了不可の場合の引渡し先・例外回復方針・必要権限を事前に決める。必要な例外回復が未合意なら開始しない。本案から強制停止や稼働中の復元を推定しない。

新方式のソース／パッケージ審査では、D01にも一致する試料、対象入替え、先行ロード、部分適用、余分な再始動、誤った位置、応答・証跡の喪失で次の変更を止めることを確かめる。過去の合成試験・リンク確認の合格は、この新しいパッケージと実行順の合格として数えない。

## 3　1試行の受入と打切り

1. **発行前。** ホスト監視とR1外の記録先を準備し、ゲスト担当がPREの認識、対象・用途、パッケージ実体、初回ロード前の条件を直前に再照合する。担当は試行番号に意図・許す効果・時刻を記録する。変更の開始前に中止できたと明示できる場合だけ「未適用」とする。
2. **適用中。** 承認票で、準備操作と、T1が最初に有効化され得る操作を特定する。準備・selectorの読戻しが計画どおりなら、T1を有効化する操作を1回だけ発行する。ここからT1の再始動とP04の初回ロードを許す。準備中に先行して有効化された場合は異常とし、予定していた有効化操作を追加しない。APIの発行、返答・エラー、実際に確認した変更、T1の再始動、最初のイメージロードは別々に記録する。一括承認はWindows操作の原子性を保証しない。返答喪失や部分成功でも再送せず、失敗後にselectorや既存リストを書き直さない。監視期限を過ぎても、Windowsが受理済みの処理が取り消されたとは扱わない。遅れて確認できた効果は別時刻で記録する。
3. **適用後。** 読み取り専用プロンプトの事後照会（POST）で再列挙し、T1/D01を個体から再同定する。最低限、下表がすべて確認されるまで「装着確認」としない。期限超過や観測不能は「効果不明」。保管できた証拠が少なくても次の試行には進まない。

| 確認する事実 | 合格に必要な証拠 |
|---|---|
| 登録と再始動 | 同じ試行・署名済みパッケージでT1だけへの登録、T1のデバイス再始動と正常な再開を時系列で裏づける。適用API成功や、後でpresentだったという一点だけでは不足。OS再起動要求、D01・親・兄弟の再始動、二度目の操作は許容しない。 |
| 初回ロード | 開始前未ロード、正しいselectorの先行、固定したSYSの初回ロードを既存の信頼できるイメージ・時刻の記録で対応づける。ドライバーのロードはゲスト単位。サービス設定・Running表示、制御デバイスの存在だけで、ロード順や装着先を断定しない。 |
| 装着位置と保護対象 | 宣言的一覧・有効スタックと、同じ試行で実際に接続されたデバイスオブジェクト列を区別する。T1は上から `partmgr → P04 → disk → stornvme`、P04は1個。`AddDevice` は未装着でも成功を返し得る。D01は元の `partmgr → disk → stornvme`、P04は0個。その他の既存上下フィルターの順序・表記、クラス、機能サービス、volume・dump設定を保ち、T1はRAW・区画0・特殊用途なし。宣言的一覧の一致だけでは実装着を確定しない。 |
| 効果と証跡 | 許したゲスト共通の差分とT1の差分を分ける。対象外への操作要求・副作用、予期しないロード、競合、未判定の差分がないことを、審査済みの実行経路・発行記録・前後差・時系列で照合する。ログ欠落を「0件」にしない。ホストはR1外の受領結果・時刻を別に記録する。 |

PnPUtilの `/stack` は有効スタックの照会である。実装着の証拠には、例えば既に承認された手段で取得済みの同時点の対象PDOに対応するデバイスオブジェクト列が使える。デバッガの新規接続、ダンプ作成やブート設定変更はこの契約に入らない。必要な証拠を得る手段がなければ事前は保留、事後は未確認とする。[PnPUtilの仕様][pnp]／[デバイスオブジェクトのスタック表示][devstack]

## 4　異常時はホスト担当がR1を判定する

| 状態 | ゲスト担当とホスト担当の対応 |
|---|---|
| 変更前に不一致。変更要求0件を確認できる | 試行を発行せず理由を記録。既に別の変更の痕跡があっても、今回の権限で消去・復元しない。所有者に引き渡す。 |
| 最初の副作用後、または副作用の有無が不明。誤一致・別位置・ロード失敗・競合・記録欠損・OS再起動要求も含む | 追加の適用、再始動、collector、修復を中止する。ホスト監視は継続する。試行は再開しない。ゲストが応答する間に、承認済みの範囲で意図・結果・最後に確認した段階と不足をR1外へ退避する。証跡のために復旧を無期限に遅らせない。成功した単発試行も同じ通常復元へ進む。 |
| ゲストが応答し、**正常終了をホストが確認** | 復旧の事前許可を照合し、通常シャットダウン後、指定するVM-Aが停止・非サスペンドであることを確かめる。ホストのWorkstationで、作成時の私的識別・親R0・OSとT1の両VMDKの連鎖が合う停止時R1だけを選び復元する。R0は保持する。名前だけで選ばず、ロック・認証・容量・連鎖が不明なら復元を実行しない。 |
| ハング、BSOD、予期しない再起動、応答喪失、正常終了不明、ホスト監視不能 | 期限と最後に確認した状態をホスト側に残し、「停止／復元未確認」として所有者に引き渡す。VMが稼働一覧から消えただけでは正常終了にしない。強制電源断、サスペンド、稼働中復元、R0への代替復元、ディスクの手動編集・削除・統合はしない。例外策は別の明示許可による。 |
| R1を復元した後 | ホストで復元結果と時刻、R0保持・R1現在位置、両ディスクの差分連鎖・接続位置を確認して通常起動する。ゲストでD01とT1を新たに同定し、OS/boot/pagefile/dump、休止、T1の状態、元のstack・フィルター・機能サービス、P04のパッケージ・登録・ロード・装着が基準に戻ったことを照合する。buildやpagefileの差分は記録し、原因不明なら「復旧未確認」で終える。 |

ホスト担当が復元を行う。ゲストへのプロンプトに復元権限は渡さない。復元後のゲスト照合は新たなPREとして採取し、ホストの復元記録と対応づける。R1はスナップショット後の変更を破棄するため、物理ホスト・外部保存先・R1外に生じた変更の回復には使えない。終了記録は「適用と装着」「観測は未実施」「R1復元と復元後の確認」の各結果を分けて返す。[基準となる復旧手順・第6節](P04-VM-A-T1-runbook.md)／[VMwareの復元時の注意][revert]
