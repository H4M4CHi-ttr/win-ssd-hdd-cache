# 実験ADR　通常ファイル実験とWindowsパイプの境界

2026-11-25 JST。適用先はローカルのx64ユーザーモード試験。製品のI/O捕捉位置・依存ライブラリの採用・公開ライセンスの判断は対象外。

## 決定

公式WinSpd v1.0B1の `stgtest-x64.exe` をクライアントにする。Windows SDKを使うC17の小さなテストプロセスに、ローカルのメッセージ型名前付きパイプの作成、接続元PIDの取得、子プロセスの寿命管理を置く。セクターの検証、キャッシュ、原本の同期、返却ステータスの決定は既存実験のRustで実行する。ランナーは自分が新規作成した2つの通常ファイルだけをデータに使う。[再現手順と実行範囲](README.md)

この境界を置く理由は、実際に接続した相手を、起動時に保持したプロセスハンドルと照合するためである。公式DLLの公開ストレージハンドルは内部構造を指すため、Win32が接続元PID照会に要求するサーバーパイプハンドルとは用途が異なる。今回のサーバーはブローカー自身がパイプハンドルを所有する。クライアントとの通信には上流の実フレームを使う。[上流のハンドル生成](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/shared/stghandle.c#L205-L226)・[Microsoftの接続元PID照会](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid)

## 所有権と終了

- CとRustは別プロセスで、匿名パイプには長さとコピー済みのバイトだけが流れる。アドレス、借用バッファ、可変メモリを共有しない。Rustは安全なファイルAPIを使い、一つの要求を最後まで処理してから次へ進む。すべてユーザーモードで、カーネルコールバックやIRQLの契約はない。
- Cの固定バッファは最大65,536バイトのデータと48バイトのヘッダーを収容する。x64レイアウトを署名確認済み配布物のヘッダーとコンパイル時に照合する。応答の `Hint` と種類を照合し、成功Readは要求ぴったりの長さ、失敗はヘッダーだけを許す。
- ランナーは内部で新規GUIDを発行し、正規の小文字のローカルパイプ名を組み立てる。最初のインスタンスだけを作り、リモート接続を拒否する。生存中の起動済みクライアントのPIDとの一致を確かめてからgeometryを送る。スレッドID由来の `Hint` は追加照合に使う。
- ブローカーは子起動前に自身を専用Job Objectへ入れる。子には標準入出力用ハンドルだけを明示継承する。通常終了は終了コード・出力・終了済みハンドルで確認する。期限切れは自分の子だけを終了して待ち、ブローカー異常終了時にもJobの最後のハンドルが閉じると残った子が終了する。外側のランナーにも独立した90秒の期限がある。[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

## 公式サーバーDLLの境界

外側では起動済みクライアントの生存と接続元PIDを確認する。内側では、別のローカルGUID名に限定して公式DLLのストレージユニットを作る。dispatcher起動前にブローカーが唯一のクライアント接続を確保し、内側サーバーのPIDがブローカー自身と一致することを確かめる。dispatcherを1本起動してgeometryとGUIDを照合する。DLLは一時フォルダー内の絶対パスでロードし、実際のロード先も照合する。通常終了ではdispatcherの終了まで内部接続を保持する。[上流のパイプ実装](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/shared/stghandle.c)・[サーバーPID照会](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid)

外部フレームを検証して1要求だけ受け付ける。別スレッドのDLLコールバックでunit、TLS要求・応答の照合番号と種類、実引数、WriteデータまたはUnmap記述子をロック下で照合する。DLLバッファは同期コールバック内だけで使用し、Rustとはコピーしたバイトを交換する。失敗Readの要求範囲はゼロ化し、DLLから戻った応答の照合番号・ステータス・長さ・データを照合して外側にはエラーヘッダーだけを渡す。

キャッシュ対応のDLLは終了時に追加のFlushを呼ぶ。停止状態・同一unit・処理中の要求なし・TLS要求と応答のHintとKindがゼロ・1回限りを確認し、Rustへ独立した原本同期を依頼する。ここで失敗した場合、既に返した外部応答は維持し、セッション全体の終了状態を失敗にする。Shutdown、dispatcherの終了待機、unitの削除が済んでから内部接続とDLLを解放する。[上流の終了処理](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/shared/stgunit.c#L252-L282)

## 原本と同期の意味

FUA writeは重なる全キャッシュを失効させて原本を書いた後、原本の `File::sync_all` 成功時にだけGOODを返す。同期だけが失敗した場合は書き込まれたバイトを巻き戻さず、古いfillを公開しない。FUA readでは原本の同期後に原本ファイルを直接読む。Flushは有効な範囲を検査し、直列化されたそれまでの原本書き込み全体を同期する。Unmapは未広告・拒否とする。通常ファイルの同期APIが返した結果が検証対象であり、物理媒体、Windowsのページキャッシュの迂回、電断後の保存結果は別の証拠を要する。[Rustの同期API](https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all)・[原本の整合性契約](../../../docs/contracts/oracle-v1.md)

Windowsへのディスク公開、ストレージフィルター、製品の配布方式を選ぶ段階では、この決定を再評価する。

## 応答喪失時の試験境界

復旧試験は、更新をDLLへ渡す直前、または適用後のGOODを外部へ渡す直前で、クライアントとのパイプだけを切断する。クライアントのWrite通信失敗・終了を独立に確かめた上で、DLLの終了時Flushを通常どおり完了させる。その後に親が原本とキャッシュを全量照合し、新規ワーカーを起動する。診断に使う標準エラーはパイプとし、原本には割り当てない。[試験条件と結果](README.md)

## 原本を扱うプロセスが失われた場合

`WorkerLoss` では、ファイルを作る親、原本とキャッシュを操作するRustワーカー、DLLをロードするブローカーを分ける。親が実際の要求・応答を中継し、ワーカーが下位書き込みの途中で制御用受領印を返した後は、応答を補わない。親は生存中の所有ハンドルを確認し、ワーカーを停止して終了を待つ。確認したEOFだけをブローカーへ中継する。ブローカーは当該Writeの応答を1バイトも受け取らずにEOFになった場合だけ、この中断経路を選ぶ。

停止後のDLL終了Flushはコールバック到着と原本への転送を区別する。失敗終了では停止済みワーカーには送らず、ブローカーも成功を報告しない。再開先の新しいワーカーは通常の終了Flushを実行する。データファイル向けの同期と、試験用制御パイプをフラッシュして通知を届ける操作は別に数える。
