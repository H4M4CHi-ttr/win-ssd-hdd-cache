# VM-Aで読み取り専用ディスク1台の列挙を確かめる

**準備段階。** WinSpd 1.0.20357 Coreの導入・アダプター開始・W0復元は完了した。次に確認したいのは、VM-AのWindowsに読み取り専用の新規ユニットが1台だけ現れ、ユニットの通常停止後に元のディスクとボリュームの構成へ戻るかである。今回作成したのは、3時点の記録を比較するオフライン検査器。実際にWindowsへユニットを公開するプログラムとゲスト記録の採取器は未実装で、実機での列挙結果はまだない。[Core単体の実測](../lab/WinSpd-VM-A-Core-W0-userready-result-2026-11-25.md)

## 先に固定する実験条件

- 対象は本人照合済みのVM-A。D01はOSディスク、元のT1は8 GiBの未初期化データディスクとして個別に照合する。新たに用意するユニットには毎回新しいGUIDを与え、16 MiB（512バイト×32,768ブロック）、空のRAW媒体、書き込み保護、Unmap非広告とする。16 MiBはこの列挙試験用の設計値。既存のVMDK、ドライブ文字、ディスク番号、利用者指定のパスをバックエンドに渡さない。
- 次の実装は、専用の一時ディレクトリに排他的に新規作成した通常ファイルを初期化し、公開前に読み取り専用で固定する。原本のハッシュを起動前・停止後に照合する。任意順の正当なReadだけを範囲内で処理し、範囲外・長さ不整合・変更要求を明示的に処理する。公開時のキャッシュ広告は無効とする。Windowsによる自動照会を記録し、書き込みテスト、パーティション作成、format、mount、offline、P04装着は行わない。
- 既存のパイプ実験では、外部クライアントの要求とDLLのコールバックを一対一で照合している。Windowsが自発的に発行するReadにはこの前提を使えない。また、固定版の既定デバイスに対する `SpdStorageUnitCreate` はその中で `SpdIoctlProvision` に到達する。ディスパッチャー開始より前に公開の作用が生じるため、作成呼び出しの前に対象・準備・承認をそろえる。[試験アダプター](../winspd_sdk.c)・[公式の作成処理](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/shared/stgunit.c#L60-L113)・[デバイス経路](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/shared/stghandle.c#L496-L561)
- 固定版miniportはユニットGUIDを文字列表現のシリアルにしてSCSI VPDで返す。書き込み保護はMode Senseと変更要求の処理にも使われる。Windowsから同じ識別子・属性が読み取れるかは実測対象。照合は新しいGUID由来のシリアルと、実際に選定したWinSpdアダプターへのデバイスの親子関係の両方を必要とする。[シリアル生成](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/sys/stgunit.c#L185-L193)・[VPD](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/sys/scsi.c#L259-L271)・[書き込み保護](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/sys/scsi.c#L560-L608)

## 記録と判定

`verify-enumeration.mjs` は標準入力のJSONだけを検査する。Node.jsからVMware・PnP・ストレージ・WinSpdを呼び出す操作はない。次の2コマンドは、合成試験と採取済み記録の判定をそれぞれ実行する。後者の `trial.json` は利用者が管理する匿名化済みの記録。2026-11-25にWindowsとDebian WSLでそれぞれ31件が成功した。正常な追加・解除、既存ディスクの置換、シリアルや親の不一致、状態不明、ボリュームの付け替え、停止後の残存、標準入力からの判定を含む。

```powershell
node --test ./verify-enumeration.test.mjs
Get-Content -Raw -LiteralPath ./trial.json | node ./verify-enumeration.mjs
```

入力の全項目と合成例は [example()](verify-enumeration.test.mjs) を参照。合格は終了値0、取得漏れ・不整合・入力エラーは1。同じブート中に採取した次の3時点を比べる。

| キー | 採取時点 | 必要な結果 |
| --- | --- | --- |
| before | Coreの開始後、ユニットの作成前 | WinSpdの対象アダプターが一意。ディスクはD01とT1の2台。元のディスク、各用途とボリュームを記録。 |
| present | 新規ユニットを公開し、PnPの列挙が落ち着いた時点 | 追加は1台だけ。予定のシリアルとアダプターが一致し、Windowsからも読み取り専用、RAW、0区画。既存ディスク・特殊用途・ボリュームに差分なし。 |
| after | ユニットの通常停止・解除後、W0復元前 | 新規ユニットが消え、D01・T1の各属性とボリューム集合がbeforeと一致。Coreのアダプターはこの時点まで存在する。 |

`plan` は公開前に確定する。sessionは本人照合済みのVM・ブート・今回の試行を結ぶトークン。osとt1は独立した照合記録で同定したディスクのキー、adapterは固定版INF・サービス・開始状態を照合したWinSpdアダプターのキー、unitSerialは公開予定のGUIDから作る期待値である。presentの候補から期待値を逆算しない。

採取器は個人パス、生のシリアルやinstance IDを出力せず、試行ごとの秘密鍵を使うHMAC-SHA256（小文字16進64桁）で識別情報を仮名化する。種別ごとに入力を分け、同じ種別の期待値と実測値には同じ正規化を使う。ディスクのkeyはPnP・ストレージの固有情報、adapterは親をたどった実アダプター、serialは独立したシリアル照会に由来する。ディスク番号は照合キーに使わない。シリアル照合ではGUID文字列の区切りと桁を保ち、大文字小文字と末尾のパディングだけを正規化する。

各phaseのadaptersは対象Hardware IDに一致する接続中の全WinSpdアダプター。開始状態または使用中INFが不明・不一致の候補を除外して1台に見せず、completeをfalseにする。disksは現在接続中の全ディスク、volumesは同じ方式で完全に列挙した**接続中PnP Volumeのキーと、そのボリュームが属するディスクのキーの組**。このVMの基準では全ボリュームがD01に属する。Get-Volumeの件数を混ぜない。各ディスクのusesにはOS、起動、稼働中ページファイル、ダンプ保存先、専用ダンプ、休止の6項目をすべて含める。照会拒否、親不明、重複、不完全な列挙、採取中の構成変化があればcompleteをfalseとして保留する。検査器単体で、採取結果の真実性、観測の間に起きた一過性の変化、コールバックでの書き込み拒否までは証明できない。

## 次の実装・VM実行の条件

1. 公開器の読み取り処理・境界値・書き込み拒否と停止経路を、パイプまたはfakeで先に実行する。特に作成成功直後の開始失敗、停止中のRead、不帰還時にオブジェクトを早期解放しないことを確認する。実デバイスへ切り替えられるオプションを既存のパイプランナーへ追加しない。
2. ゲストの採取器が、あらかじめ保存したD01・T1の個体・用途を取得できること、仮名の対応が維持されることを確認する。公開器と採取・停止手順を、実機適用前に独立レビューする。
3. VM-AでのCore再導入・初回ロード、新規ユニット1台の公開と解除、正常終了後のホストからのW0復元・再起動を、次の試行の許可範囲として確認する。前回のCoreはW0復元で消えている。復元で失う別作業があれば開始しない。
4. 不一致、想定外のディスク／ボリューム、書き込みの受理、制限時間内に停止を確認できない場合は採取・公開を打ち切る。データをホストに退避し、正常終了できる場合だけホストからW0へ戻す。正常終了できない場合は保留とし、強制電源断や別の復元点への切替を自動で行わない。復元後はCoreの登録と試行ファイルの消失、D01/T1の個体と用途、R0・R1・W0の保持を確認する。
