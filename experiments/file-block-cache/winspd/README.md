# 公式stgtestと通常ファイルのキャッシュをWindowsで検証する

2026-11-25 JST。Windows x64（build 26300）、PowerShell 7.6.9、.NET 10.0.14の通常ユーザーで、公式の `stgtest-x64.exe`、自作のローカルパイプサーバー、既存のRustキャッシュを接続した。データは各シナリオが新規作成する `origin.img` と `cache.img` の2本に限定する。直接転送の9シナリオに続き、公式サーバーDLLを通る13シナリオも検証した。VM-Aでは後にminiportの起動とW0復元を確認した。Windowsへの仮想ディスク公開は未試験。[Core単体の実測](lab/WinSpd-VM-A-Core-W0-userready-result-2026-11-25.md)。[設計判断と所有権](ADR.md)

## 再現

x64のMSVC・Windows SDKを使えるPowerShell 7.2以降、リポジトリで固定したRust 1.99.1、ローカルのCargo依存キャッシュ、7-Zipが必要。公式リリースの `winspd-1.0.20357.msi` を通常ファイルとして用意し、リポジトリのルートから次を実行する。インストーラーは起動しない。[WinSpd v1.0B1公式リリース](https://github.com/winfsp/winspd/releases/tag/v1.0B1)

```powershell
.\experiments\file-block-cache\winspd\run.ps1 -Package '.\winspd-1.0.20357.msi'
```

ランナーはパッケージを読み取り専用で開き、SHA-256を照合する。指定モードに必要な試験クライアント、ヘッダー、サーバーDLLを一時フォルダーへ展開し、Cブローカーをビルドする。クライアントの実行ファイルも照合し、試験終了まで書き換えを防ぐ共有モードで開く。今回取得したMSIのAuthenticode署名は `Valid`（NAVIMATICS LLC）。内部のEXEには単独のAuthenticode署名がない。

| 検証対象 | SHA-256 |
| --- | --- |
| 公式MSI | `F1157EEF805DCBEC78A477F2B4EE5ABC0049C8A9329444E5D18CAB01D3604265` |
| 内部のx64クライアント | `FF53AE37AD610AA851765596B3E821BD28CF2F0F68AD30991C79B423A3FB0AB7` |

実通信を完走したのは検証用のローカル作業ツリー。共有ストレージでは同じ内容の `run.ps1` がWindowsの実行ポリシーにより署名を要求され、直接起動を拒否された。スクリプトのブロック解除やポリシー変更は行っていない。[パスやプロセスIDを除いた実行記録](verified-run.txt)

## 直接転送モードで確認した9シナリオ

| 条件 | 照合した結果 |
| --- | --- |
| 通常Read/Write/Flush | `WRRF` を2巡。8要求、原本同期2回。2回のwarm Readでは原本ハンドルを書き込み専用にし、計3キャッシュラインから正しいデータが返った。クライアントは `OK` |
| FUA | `CacheSupported=0` で公式クライアントがFUA付きWriteとReadを発行。Write後、Read前、明示Flushの計3回、原本を同期した。Readは原本へ1回、キャッシュへ0回。クライアントは `OK` |
| FUA Writeの同期失敗 | 通常ファイルへの書き込み完了を別ハンドルで確認した時点で同期エラーを注入。新しいバイトを保持し、CHECK CONDITIONを返した |
| FUA Readの同期失敗 | 同じ原本を読み取り専用で開き、Windowsの `sync_all` が返したOSエラー5を直接照合。データ読み取り0回、CHECK CONDITION |
| Flushの同期失敗 | 読み取り専用の原本でWindowsのOSエラー5を照合し、CHECK CONDITION |
| Unmap | 能力は未広告。明示要求へILLEGAL REQUESTを返し、両ファイルの内容を保持 |
| 意図的に壊した成功Read | 正しいRustの結果を照合した後、GOOD応答の1バイトだけを変更。公式クライアントが `bad buffer: after Write` を検出 |
| 接続元照合の負例 | 想定PIDを意図的に変えると、起動した公式クライアントでもgeometry送信前に拒否。Rust側への要求0件 |
| 応答停止 | 1要求受信後、親がパイプを開いたまま応答を保留。専用の2秒期限でブローカーが子を終了して回収し、タイムアウトを報告 |

SCSIエラーの4例は、種類・照合番号・応答長・senseに加え、公式クライアントの条件検査失敗と終了値1117を照合する。破損データの負例は同じ終了値でも診断文が異なる。タイムアウトは1460で別判定とする。各シナリオで子の終了を確認し、最終的に `FILE_CACHE_WINSPD_OK` と対象試験1件の成功がそろう。Windowsの実通信は、上記スクリプトが通常のCargo試験とは別の1件として実行する。通常ファイル試験はWindows・Debian WSLともにdebug・releaseで各23件成功、ワークスペース全体はWindows 365件、Linux 367件成功した。Linuxのreleaseビルドでは、リンカーが既存の非推奨の最適化指定を無視する警告が出た。

## 公式サーバーDLLの実測

```powershell
.\experiments\file-block-cache\winspd\run.ps1 -Package '.\winspd-1.0.20357.msi' -Transport ServerDll
```

固定DLLは `winspd-x64.dll`、ファイル版 `1.0.20357.55c53bc`、SHA-256 `35433B6E99C4B282A7EC07757F2206851F28DABF7BBCFFD90BF60F317E865F7B`。展開時のAuthenticode署名は `Valid`。ランナーはDLLを読み取り共有で保持し、ブローカーはロードしたモジュールの絶対パスを照合する。公式クライアントの要求は外側のパイプからDLLの内側のパイプへ進み、DLLの公開コールバックがRustへ転送する。応答は逆の経路を戻る。[匿名化したDLL実行ログ](verified-server-dll.txt)・[公開インターフェース](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/inc/winspd/winspd.h)

| 条件 | 観測した結果 |
| --- | --- |
| 通常の8要求とFUAの3要求 | 通常は外部要求に伴う同期2回と終了時の同期1回。FUA列は外部要求に伴う同期3回、終了時の追加同期0回 |
| 書いた直後にFUA Readで原本同期エラーを返す | エラー5を確認。内側応答のデータ部1,024バイトはすべてゼロ。クライアントへのエラー応答はデータ0バイト |
| クライアント成功後に終了時Flushだけ失敗 | Write・Readは成功し、公式クライアントは終了値0。終了時の原本同期でエラー5を受け、ブローカーは終了値29。試験はこの失敗を観測した場合にだけ合格 |
| 内側が既に使用中、または外側のPIDが不一致 | geometryを渡す前に停止し、Rustへの転送は0件 |
| 承認済み要求との照合不一致 | 外部からは1件受信、DLLコールバックで1件を拒否、Rustへの転送0件。ブローカーは拒否件数から終了値13を返した |
| その他の負例 | Write・Read・Flushのエラー、Unmap拒否、1バイト壊した成功応答、返答停止時の子回収も検査。期限負例は強制終了の試験で、正常なDLL終了Flushの証拠には含めない |

実測はWindows x64の検証用ローカルツリーで実施。DLLモードの合格には13シナリオの結果と `FILE_CACHE_WINSPD_SERVER_DLL_OK` が必要。クライアントだけを使った従来の直接転送では、新しい終了時Flushの検査が失敗した。

## 応答を失ったWriteの再開試験

```powershell
.\experiments\file-block-cache\winspd\run.ps1 -Package '.\winspd-1.0.20357.msi' -Transport Recovery
```

公式クライアントから、LBA 7・8（計1,024バイト）に `Read / Read / Write` を発行する。先に2本の4 KiBラインを旧版で温め、最後のWriteについて外側のパイプを切断する。送信先の名前は従来どおりランナーが内部で決める。クライアントのWriteの診断、アドレス・長さ、終了コードを照合し、子の終了を待つ。[匿名化した実行記録](verified-recovery.txt)・[復旧試験コード](recovery_checks.rs)

| 最後のWriteの切断位置 | 公式クライアント | 最初のワーカー終了後の原本 | 同じ時点のキャッシュ | 次のプロセスの初回Read |
| --- | --- | --- | --- | --- |
| 外側で受信し、DLLに渡す直前 | 通信エラー233、Write応答0件 | 全体が旧版 | 両ラインとも旧版 | 原本から旧版 |
| 原本の更新後、DLLのGOODを受け取り、外側へ送る直前 | 通信エラー233、Write応答0件 | 該当1,024バイトだけ新版 | 両ラインとも旧版 | 原本から新版 |

各ケースの親が2ファイルを排他的に新規作成し、削除と改名を許さないハンドルを保持する。最初のRustワーカー、そのブローカー、公式クライアントの終了後に、親は原本67,072バイトとキャッシュ8,192バイト全体を独立した期待値と比較する。その後で新しいRustワーカー・DLL・公式クライアントが同じ2ファイルを使う。子が開けるのは専用ステージの親所有ディレクトリ内の固定ファイル名。子の標準入出力はデータファイルから分離した。

再開後の `Read / Read` では、最初が原本2ライン、次がキャッシュ2ラインとなる。両方の返却バイトとファイル位置を検査する。先行Writeを持たない `RR` では、公式クライアント自身はデータ内容を検査しないため、独立期待値との比較をRust側で行う。書き込みデータの照合には、固定版のLBA別パターンを使う。[上流の書き込みパターン](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/stgtest/stgtest.c#L434-L458)・[上流のRead照合条件](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/stgtest/stgtest.c#L640-L668)

対照試験でWrite応答をそのまま返すと、公式クライアントが成功して試験は失敗した。別の使い捨てコピーで旧スロットを起動時から有効扱いにすると、適用後のケースでは返却バイトの不一致、適用前のケースでは同じバイトでも初回が誤ってヒットしたことで検出した。

切断後もDLLの終了時Flushは稼働し、各ワーカーで原本の同期1回が成功した。クライアントからは同じエラーに見えても、適用済みかどうかは区別できない。ここで比較したのは応答の喪失と正常な終了Flushを経た再開であり、ワーカーのクラッシュや電断による耐久性は別の検証を要する。

## 終了時の原本同期を経ないワーカー停止

```powershell
.\experiments\file-block-cache\winspd\run.ps1 -Package '.\winspd-1.0.20357.msi' -Transport WorkerLoss
```

公式クライアントの `RRW` で2つの4 KiBラインを温める。最後のWriteはLBA 7・8にまたがる1,024バイト。実験用の下位writerは、要求全体の検証とキャッシュ失効が済んだ後に、原本の通常ファイルへ指定した長さだけ書いて待機する。親は全原本67,072バイトと旧キャッシュ8,192バイトを別ハンドルで確認し、自分が起動したRustファイルワーカーだけを停止・回収する。ブローカーと公式クライアントはこの時点で別プロセスとして動いている。[試験コード](abrupt_checks.rs)・[匿名化した記録](verified-abrupt.txt)

| 停止前に原本へ書いた長さ | 再開後のLBA 7 | 再開後のLBA 8 | 公式クライアントのWrite |
| ---: | --- | --- | --- |
| 0バイト | 旧 | 旧 | 通信エラー233 |
| 512バイト | 新 | 旧 | 通信エラー233 |
| 1,024バイト | 新 | 新 | 通信エラー233 |

親はファイルワーカーの終了と無応答のEOFを確認してから、そのEOFをDLL側へ伝える。ブローカーは外側へWrite応答を送らずに接続を切り、対象Writeのエラー診断と公式クライアントの自然終了を照合する。DLLの終了Flushコールバックは1回到着し、停止した原本側への同期は0回。ブローカーは失敗終了値31を返す。親は両ファイルを再び全量照合し、新しいRust・公式DLL・公式クライアントを起動する。最初のReadは原本2ライン、次はキャッシュ2ライン。再開側の終了時同期は1回成功した。

3条件を3回繰り返して同じ結果を得た。専用コピーの対照試験では、報告した512バイトより余分に書いた場合は親の全量照合が失敗し、停止済みワーカーへ終了同期を要求した場合は予期しない制御要求を検出した。通常試験はWindows・Linuxともdebug／releaseで各28件成功し、ワークスペース全体はWindows 370件、Linux 372件成功した。

512バイトの結果は、下位writerにその位置で実際に停止点を設けて得たもの。同一OSのファイルAPIから読めたバイトを示す。Windowsが1回のWriteを自然に分割したこと、物理媒体への到達、セクターの原子性、電断後の保存結果は測定していない。既存の `Recovery` は正常な終了時Flushを経る別条件として再実行した。

## 読み取り専用プロファイル

```powershell
.\experiments\file-block-cache\winspd\run.ps1 -Package '.\winspd-1.0.20357.msi' -Transport ReadOnly
```

将来Windowsにディスクを見せる場合に備え、まずパイプ上で書き込み保護を検証した。公式DLLのgeometryを照合して外側へ送り、`WriteProtected=1` かつ `UnmapSupported=0` を確認した。読み取り専用フラグだけを立てた対照では、公式クライアントのWriteがRust側まで届き、試験が失敗した。現在は親が承認した要求とDLLコールバックの一致を照合し、変更要求をその場で拒否する。[試験コード](readonly_checks.rs)・[匿名化した実行ログ](verified-readonly.txt)

| 公式クライアントの要求 | 観測した結果 |
| --- | --- |
| 読み取り2回 | 初回は原本2ライン、2回目はキャッシュ2ライン。全バイトを独立期待値と照合 |
| 読み取り後のWrite／FUA付きWrite | 原本と異なるデータを送信。応答はCHECK CONDITION、sense `07/27`（書き込み保護）。RustへのWrite転送0件 |
| 読み取り後のUnmap | 未広告の要求を `05/20` で拒否。Rustへの転送0件 |
| FUA Read | キャッシュ非広告のセッションで原本同期1回、原本から直接Read 1回、キャッシュRead 0回 |
| 明示Flush | キャッシュ広告ありで `07/27`、なしで `05/20`。いずれも外部要求による同期0回。広告ありでDLLが発行する終了時Flushは、実際の原本同期1回で別に完了 |

RustのReadは読み取り専用ハンドルを使う。Windowsで同期に必要な書き込みアクセスは、同じテスト原本の同期専用ハンドルに限った。これを保持している間は別の書き込みアクセス・削除アクセスのオープンが共有違反となることを検査した。7件すべてで原本全体の不変を確認した。

ここで観測したsenseはユーザーモードのパイプ応答。固定版miniportのソースでは、キャッシュ未広告のFlushと未広告Unmapが先に `SRB_STATUS_INVALID_REQUEST` になる。Windowsでのディスク属性・PnP列挙・ドライバーの受理は未検証である。[miniportの判定順](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/sys/scsi.c#L560-L608)・[次のVM事前調査の範囲と配布物の監査](vm-preflight.md)

終了ステータスだけを合格条件にしないことも確認した。使い捨てコピーでWrite応答のsenseを `05/24` に変えた場合と、拒否動作を保ったまま外部向けgeometryの保護ビットだけを落とした場合は、それぞれ想定した箇所で失敗した。

## 適用範囲

1要求ずつ処理し、成功Readは要求と同じバイト数を返す。上流クライアントは同じLBAへの書き込みに同じデータを使い、短い成功Readの不足分をゼロで補う。独立した2版データ試験と応答の厳密な長さ検査を併用する。[上流のクライアント実装](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/stgtest/stgtest.c#L163-L187)・[2版データ試験](../sector_checks.rs)

FUA・Flushの実測は、通常ファイルに対するOS同期APIが返した結果まで。電断後の永続性、物理HDD/SSDの性能、OS外部からの書き込みの捕捉、P04の実登録は別の検証対象である。
