# 通常ファイルでのブロックキャッシュ実験

WindowsとLinuxのテストランナーが、新規の `origin.img` と `cache.img` を使って、ファイルから実際に返ったバイトと読み取り元を検証する。原本だけが正本で、キャッシュのメタデータはセッションごとに空から始める。実験は[D03の疑似媒体](../ocf-portability/README.md)から分離し、`cache-model` のライブラリにはファイルI/Oを追加しない。

2026-11-25に、公式WinSpdの試験クライアントとWindowsの名前付きパイプで往復した。公式サーバーDLLの13シナリオに続き、Write応答喪失後の正常終了と、原本ワーカーを途中停止してからの再開も検証した。通常ヒット、FUA、Flush、同期エラーと停止時の回収は[Windows実測と再現手順](winspd/README.md)を参照。以下の初期結果とセクター単位の結果は当時の到達点である。

OSへの公開前に、書き込み保護を広告した公式DLLでも7条件を検証した。次の未検証項目は、VM-Aのドライバー受理条件とWindowsからのディスク列挙である。[配布物の監査と次の事前調査](winspd/vm-preflight.md)

## 入出力と範囲

- 原本を4 KiBのブロックに分け、2つのキャッシュスロットへ直接対応付ける。原本の末尾に短いブロックがある場合は、その実長だけを扱う。原本への部分書き込みは、重なるすべてのブロックを先に失効させる。
- 1セッションの操作は単一の所有者が順に実行する。通常の読み取りは有効なスロットを試し、欠落・キャッシュ読み取り失敗時には原本を読む。原本から取得したバイトの格納が失敗しても原本の成功は保持する。原本側の失敗は呼出し側に返す。
- 原本から採取済みで、キャッシュファイルへの書き込みと公開をまだ終えていないfillを1件だけ保持できる。そのスロットを予約し、重複する原本書き込みがあれば公開権を失効させる。予約中に同じスロットへ対応する別ブロックを読んだときは原本へ迂回し、予約を奪わない。残った古いバイトがスロットに実際に書かれる場合も、公開してよいのは現在有効なfillの書き込みが完了した場合だけである。
- 入出力先はテストが専用の一時ディレクトリ内に新規作成した通常ファイルに限定する。通常操作では原本の変更をすべて実験の書き込み経路に通す。故障試験の切詰めは専用fixtureに限る。利用者のファイルパスを入力するCLIは設けない。

## 受入条件

1. 安定したブロックは、cold時に原本を読み、warm時にキャッシュファイルを実際に読む。テストが独立に用意した期待バイト、原本とキャッシュの読み取り回数、キャッシュファイルに残った内容を照合する。warm時には、同じ原本ファイルを書き込み専用で開き直す。原本を読めない状態で正しい値が返り、複製したキャッシュハンドルの共有ファイル位置が読み取り終端まで動くことを確認する。
2. Aを採取したfillを保留し、重なる原本範囲をBに更新した後でfillを完了する。古いAがキャッシュファイルに書かれても公開を拒否し、次の読み取りは原本のBを返す。操作順をテストが固定する。
3. 有効なキャッシュの読み取りが失敗すれば原本のバイトに戻る。原本側も失敗した場合は、そのエラーを保持する。原本書き込みの失敗でも古いヒットを復活させない。
4. 親が作成した2ファイルのハンドルを子に渡す。warm状態を作った子の終了後、親が原本をBに更新し、キャッシュにAが残っていることを直接確認する。別プロセスで開いたキャッシュの最初の読み取りが原本のBになり、次はキャッシュからBを返すことを確認する。

対象はファイルAPIとこの順序付けの範囲である。カーネルでの非同期完了、外部からの原本変更の捕捉、耐電断性、実HDD/SSDの速度は別の検証を要する。[F09の依存条件](https://github.com/H4M4CHi-ttr/win-ssd-hdd-cache/issues/27)とP04の実登録判定は変更しない。

## 再現

リポジトリのルートから、固定ツールチェーンで実行する。

```sh
cargo test --locked --offline -p cache-model --test file_block_cache -- --nocapture
```

現在の通常実行では計28件（初期12、セクター6、同期4、フレーム検証1、比較3、部分書き込みと事前失効2）が走る。`ignored` の再起動用ヘルパーは、再起動試験の親が2回明示的に起動する。ヘルパーは受け取った通常ファイルの長さと内容を確認し、各段階の検査に通ると完了印を返す。親は終了コードと完了印の両方を照合する。

## 512バイトのセクター要求（2026-11-24時点）

原本の長さが正の512バイト倍数の場合に、1要求あたり1〜128セクター（最大64 KiB）の読み書きを受け付ける。開始位置は論理ブロックアドレス（LBA）で指定する。書き込みは要求全体の範囲とデータ長を検証してから、既存の失効処理を通して原本に渡す。読み取りは必要な4 KiBラインから該当部分を集め、すべて成功してから返す。途中の原本エラーは呼出元に返す。この時点ではFUA（Force Unit Access）付きの読み書き、Flush、Unmapは `Unsupported` を返し、両ファイルに作用しない。

LBA 7・8は4 KiB境界をまたぐ。試験はここに異なる2版を書き込み、前後のセクターを含む原本と両方のキャッシュラインを独立した期待値で検査する。ほかに、128セクターの要求、短い最終ライン、範囲・データ長の不正、2ライン目の読み取りエラー、既に採取した古いfillの完了を試す。[セクター試験のソース](sector_checks.rs)

```sh
cargo test --locked --offline -p cache-model --test file_block_cache -- cache::tests::sector_checks::
```

| 2026-11-24の実行結果 | Windows x64 | Debian Linux（WSL） |
| --- | ---: | ---: |
| 通常ファイル実験（追加6件を含む） | debug・releaseとも18件成功 | debug・releaseとも18件成功 |
| ワークスペース全体 | 360件成功 | 362件成功 |

追加6件は要求処理の実装前にすべて失敗した。Windowsでは、LBAを4 KiB単位で換算する、失効を飛ばして原本を書く、途中エラーを部分成功にする、FUAを黙認する、という4種類の誤実装を個別に試し、それぞれ該当の試験が検出した。

### 2026-11-24に設定した接続条件

公式の `stgtest` は同じLBAへの書き込みに同じパターンを使うため、更新前後を区別する2版試験は接続後も必要になる。また、`CacheSupported` が偽のときは通常のRead/WriteにもFUAが付く。フラグを切り替えて試験を通すと、検証していない能力を報告するおそれがある。実接続前には、広告する機能と原本に対するFUA・Flushの実動作を合わせる必要がある。[上流のパターン生成](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/stgtest/stgtest.c#L434-L458)・[要求生成](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/stgtest/stgtest.c#L605-L630)

上流には開発用の名前付きパイプ経路と実デバイス経路があり、クライアントとサーバーの両方が名前の接頭辞で選択する。将来の接続試験では、実行器が内部で作ったローカルパイプ名に対象を固定する。この18件ではRust関数に直接要求を渡した。翌日に実施した公式クライアントとの通信結果は上記のWindows実測に記録した。[公式チュートリアル](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/doc/WinSpd-Tutorial.asciidoc#testing-during-development)・[クライアントの分岐](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/stgtest/stgtest.c#L387-L402)・[サーバーの分岐](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/shared/stghandle.c#L525-L541)

## 2スロットのキャッシュで原本の読み取りを何回省けるか

各要求列について、新規の通常ファイルを使い、原本直読とキャッシュ経由を独立に実行した。1回のReadは4 KiBで、各方式・各列で4 MiBすべての返却バイトをメモリ上の期待値と照合した。最後に両方式の原本全体も比較した。Windows x64とDebian Linux（WSL）の結果は一致した。[比較試験のソース](workload_checks.rs)

| 固定した要求列 | 原本直読時の原本Read | キャッシュ利用時の原本Read | キャッシュヒット |
| --- | ---: | ---: | ---: |
| ライン0・1を交互に読む。2本が別スロットに収まる | 1,024 | 2 | 1,022 |
| ライン0・2を交互に読む。2本が同じスロットを使う | 1,024 | 1,024 | 0 |
| ライン境界をまたぐ1 KiBの上書き128回、同じ2ファイルでセッションを開き直す操作7回を含む | 1,024 | 528 | 496 |

混合列では、毎ラウンド、上書きで失効した2ラインとスロットの置き換えで2ラインを原本から読む。8回のセッション開始時だけ、さらに2ラインを読む。したがって原本Readは `128 × 4 + 8 × 2 = 528` 回になる。対照として、キャッシュ利用側も常に原本を読むようにすると、常駐列と混合列は失敗し、衝突列だけが成功した。

測定値はキャッシュ処理が原本ファイルを読む回数。読み取り元はOSに見えるファイル位置と内部カウンターの双方で確認した。検査用のseek・原本最終照合は集計に含めていない。キャッシュへの書き込みを含む総I/O、物理ディスクのI/O、応答時間、速度向上率は未測定である。

```sh
cargo test --locked --offline -p cache-model --test file_block_cache -- cache::tests::workload_checks:: --nocapture
```
